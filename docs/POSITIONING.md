# ContentX 产品定位

本文档是 ContentX 对外定位、差异化价值、选型比较和产品方向判断的统一口径。它不代替功能事实：[项目状态](./STATUS.md)记录已经交付的能力，[产品需求](./PRD.md)定义承诺与非目标，[路线图](./ROADMAP.md)记录尚未完成的工作。

## 1. 一句话定位

**ContentX：面向开发者和 AI Agent 的自托管 Headless CMS。**

产品目标：成为人和 AI Agent 共用的自托管内容控制平面，使内容变更可授权、可审批、可追踪、可回滚。当前服务端以 Go 构建；这是实现和运维选择，不要求客户端、SDK 或扩展使用 Go，也不单独构成产品壁垒。

ContentX 让团队在自己的基础设施和数据边界内管理、治理与交付内容。开发者通过 REST、只读 GraphQL 和 OpenAPI 集成应用；AI Agent 通过 MCP，在明确的身份、权限和发布工作流内操作内容。尚未闭环的审批、审计与回滚能力以[项目状态](./STATUS.md)和[路线图](./ROADMAP.md)为准。

## 2. 为谁解决什么问题

ContentX 主要服务两类使用者：

| 使用者 | 需要解决的问题 | ContentX 的回答 |
|---|---|---|
| 开发者与平台团队 | 需要一个可自托管、接口清晰、便于接入现有应用和基础设施的内容后端 | 语言中立的 REST/OpenAPI、只读 GraphQL、多数据库、Docker Compose 与可观测性；当前核心以 Go 实现 |
| AI Agent 构建者 | 需要让 Agent 读写内容，同时不能绕过身份、权限和发布治理 | stdio/HTTP MCP、HTTP 模式 API Token、权限检查、显式发布与冲突保护 |

管理员、编辑和作者通过管理后台参与内容生产与治理。他们是重要的日常使用者，但产品差异化首先来自开发者接入和 Agent 受控操作，而不是把管理后台扩展成封闭的一体化建站工具。

## 3. 核心优势

### 3.1 自托管优先，当前核心以 Go 构建

- 当前后端以 Go 构建，保留清晰的部署、并发和运维路径。
- 支持 Docker Compose，以及 SQLite、PostgreSQL、MySQL、本地文件和 S3 兼容存储。
- 团队自行掌握部署、数据、备份恢复和观测边界。
- Go 同时会约束贡献者、招聘和插件作者，不能把语言本身当作已验证的市场优势。
- 公共 REST/OpenAPI、MCP、事件和 SDK 不得依赖内部 Go 类型；当前 Go Plugin interface 只作为内置插件边界。

这项选择不应写成未经基准验证的“性能最快”或“资源占用最低”。在取得真实采用和维护成本证据前，采用“Go 核心 + 语言中立契约”的可逆方案，具体决策与退出条件见 [ADR-001](./ADR-001-language-and-extension-boundary.md)。

### 3.2 开发者接口优先

- REST 是主要读写接口，OpenAPI 是可验证的接口契约。
- GraphQL 提供公开只读查询，避免将尚未交付的写能力包装成承诺。
- API Token、Webhook 和多种接口协议便于应用、脚本与自动化流程接入。

### 3.3 AI Agent 是一等客户端

- 内置 stdio 与 Streamable HTTP MCP，而不是只提供一段外部集成示例。
- 创建、更新和发布工具检查对应权限；HTTP MCP 使用带明确权限的 API Token。
- Agent 写入遵守显式发布和乐观锁边界，不能把自动化等同于绕过内容治理。

后续 AI 能力应继续围绕“可授权、可审计、可审批、可限流”建设，再扩展 RAG、Embedding、向量搜索和内容生成辅助。

### 3.4 内容工作流与安全边界并重

- 提供草稿、审核、发布、取消发布、定时发布、归档和修订历史。
- 提供 JWT、刷新令牌轮换、API Token、TOTP、RBAC、限流和审计日志。
- 公开接口不返回草稿、私有或受密码保护内容，关键边界有明确测试要求。

### 3.5 可运维、可恢复、可验证

- 提供迁移、备份恢复、健康检查、结构化日志、Prometheus 和 OpenTelemetry。
- 质量门禁覆盖 Go、前端、浏览器 E2E、静态检查和 OpenAPI 漂移。
- 外部服务能力要求真实兼容服务验证，已完成范围与限制分别记录，不用路线图代替事实。

## 4. 与常见方案的选型差异

ContentX 不宣称在所有场景取代成熟产品。以下比较描述的是产品起点和优先级，不是逐项功能胜负；竞品版本、部署方式和商业方案变化时，应以其官方文档为准。

| 代表方案 | 典型产品重心 | ContentX 的差异化取向 | 更适合选择 ContentX 的情况 |
|---|---|---|---|
| [Strapi](https://docs.strapi.io/) | Node.js 生态、即时 API、插件与原生 MCP | 自托管内容控制、语言中立契约和受治理的 Agent 变更路径 | 团队更看重部署与数据边界、审批和可追踪性，而非插件数量 |
| [Directus](https://docs.directus.io/getting-started/architecture) | 从现有数据库出发的数据平台体验 | 从内容模型、发布工作流和开发者/Agent 接口出发 | 团队要建设受治理的内容流程，而不只是为现有数据库增加管理界面 |
| [Payload](https://payloadcms.com/docs/configuration/overview) | TypeScript、Next.js、代码优先配置与 MCP 插件 | 独立内容服务，通过语言中立的标准契约对接不同前端和 Agent | 团队不希望 CMS 与特定全栈 JavaScript 框架深度绑定 |
| [Sanity Content Lake](https://www.sanity.io/docs/content-lake) / [Studio](https://www.sanity.io/docs/studio/deployment) | 托管 Content Lake 与可定制 Studio | 自主管理服务、数据和运维边界，内置受控 MCP 工具 | 运行环境和核心数据服务需要自主管理，并希望 Agent 复用内容权限和工作流 |

选择边界同样需要说清：如果项目首先需要庞大的现成插件市场、特定 JavaScript 全栈框架的深度融合，或完全托管且尽量免运维的服务，应先评估对应侧重的成熟方案。ContentX 的价值来自一组一致的取舍，而不是功能数量最多。

以上竞品资料于 2026-08-22 根据各产品官方文档重新核对；Go、MCP 或 RAG 均不再单独作为独占差异，后续引用时仍需重新核验。证据与日志方向见 [RESEARCH-001](./RESEARCH-001-market-and-observability.md)。

## 5. 产品方向优先级

后续路线按以下顺序判断，既有多租户、RAG、Release 与 SDK 阻断项继续并行收口，不因顺序调整而消失：

0. 明确语言与扩展边界：先验证“Go 核心 + 语言中立契约”，不在缺少证据时直接重写。
1. 补齐 Headless CMS 本体：公开动态内容交付、安全的内容模型演进、真实后端 E2E 和发布制品一致性。
2. 闭环生产信任边界：多租户、Token/MCP principal、RAG 生命周期、外发、成本和恢复验证。
3. 交付受治理的 Agent 黄金路径：提议、确定性校验与 diff、审批、独立发布、审计和回滚。
4. 升级日志、审计和可观测性：统一事件、敏感数据规则、关联 ID、高风险 outbox、导出和告警。
5. 改善开发者采用与平台能力：持久向量后端、多语言 SDK、框架示例和部署模板；外部插件在需求验证后推进。
6. 用设计合作伙伴、首次发布时间、受治理 Agent 修改时间、审计完整率和持续使用率验证市场。

每个候选功能至少回答三个问题：是否强化自托管和数据控制；是否改善开发者或 Agent 的真实工作流；是否具有清晰的权限、恢复和验证路径。无法回答时，不应因为竞品具备该功能就自动进入路线图。

## 6. 文案规则

### 标准写法

- 首次介绍优先使用本页的一句话定位，不再混用“博客系统”“低代码平台”或泛化的“AI CMS”作为主定位。
- 展开介绍时按“自托管与数据边界 → 开发者接口 → 受控 Agent 操作 → 当前 Go 实现与运维取舍”排序。
- 对比竞品时说明选择取向和适用场景，不贬低竞品，不暗示未经验证的功能差距。
- 已交付能力引用 `STATUS.md`；未完成能力必须标注为“当前里程碑”“候选方向”或“尚未交付”。

### 避免的表述

- 未经基准验证的“最快”“最轻”“性能碾压”。
- 未经安全审计或认证支持的“最安全”“企业级合规”。
- 将建设中的多租户、RAG、完整 GraphQL、外部插件或商业化能力写成已交付。
- 用“支持 AI”笼统替代 MCP、权限、工作流和审计等可验证边界。
- 把“使用 Go”“支持 MCP”或“具有 RAG”单独写成已经成立的市场壁垒。
