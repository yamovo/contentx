Advantages

为可控的内容基础设施而生

ContentX 把开发者体验、Agent 接入和内容治理放在同一套清晰边界里

🏠

数据与部署归你

默认走自托管路线，可选 SQLite、PostgreSQL 或 MySQL，以及本地文件或 S3 兼容对象存储。

⚙️

开发者优先

REST 作为主要读写接口，并提供 OpenAPI 契约、只读 GraphQL 与语言中立的集成边界。

🤖

AI Agent 原生入口

同时提供 stdio 与 Streamable HTTP MCP；HTTP 模式通过 API Token 授权写工具，不让 Agent 绕过业务规则直连数据。

📝

发布过程可治理

草稿、提交审核、发布、取消发布、定时和归档一条链路，辅以修订历史与乐观锁冲突保护。

🔌

内容交付不绑前端

同一份内容可交给网站、App、内部工具或自动化流程；Webhook、RSS 与 API 负责衔接现有技术栈。

🛡️

生产基础内置

JWT、刷新令牌轮换、API Token、TOTP、RBAC、审计、限流、备份恢复与可观测性共同守住运行边界。

Positioning

不是谁替代谁，而是默认路线不同

如果你需要的是自托管、Go 技术路线和可治理的 Agent 内容操作，ContentX 会更顺手

关注点一体式 CMS通用 Headless CMSContentX
默认交付方式页面、主题与内容管理紧密结合以 API 或 SDK 向多端交付内容REST 读写 + 只读 GraphQL + OpenAPI 契约
部署与数据通常与网站运行环境一起管理可托管或自托管，取决于具体产品自托管优先；数据库和对象存储由团队选择
Agent 接入通常需要自行桥接内容能力多通过 API、SDK 或产品生态集成内置 stdio 与 Streamable HTTP MCP
Agent 写入治理取决于插件与既有工作流取决于产品权限模型与集成方式沿用 API Token / RBAC；创建默认草稿，发布需要独立权限
更适合站点页面与内容编辑高度一体的项目需要成熟生态或托管服务的多端项目偏好 Go、自有基础设施与受控 Agent 自动化的团队

以上比较描述常见产品路线，不代表所有产品；其他 Headless CMS 也可能支持自托管，具体能力以各产品版本和部署方案为准。

Built For

适合这些团队

把 ContentX 当作统一的内容后端，而不是另一个要迁就的页面系统

🧑‍💻

产品与平台开发团队

前端框架、终端形态和发布节奏由你决定，ContentX 提供稳定的内容模型、接口契约与管理后台。

  • 网站、App 与内部工具共用内容
  • 需要 REST、OpenAPI 或只读 GraphQL
  • 偏好 Go 与容器化部署
🤖

AI Agent 与自动化团队

通过标准 MCP 接入内容资源和工具，让 Agent 在显式授权范围内参与创作、更新与发布流程。

  • stdio 与 Streamable HTTP 两种传输
  • HTTP MCP 写入默认进入草稿
  • 发布权限与日常写入分离
🔐

重视数据边界的组织

把数据库、对象存储、密钥和运维节奏掌握在自己的基础设施中，同时给编辑团队清晰的日常工作台。

  • RBAC、TOTP 与关键操作审计
  • 备份恢复和迁移可重复
  • 指标、追踪与健康检查可接入
