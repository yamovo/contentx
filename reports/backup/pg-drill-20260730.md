## 结论

## 迁移验证

### 空库路径

全新 PostgreSQL 启动后自动应用 v1–v7，public schema 共 30 张表，`schema_migrations` 最大版本为 7。

### 含数据升级与回滚路径

创建并发布文章 `ContentX b11117c Restore Drill` 后停止应用：

1. 回滚 v7、v6 到 v5，确认 `articles.version` 列和 `webhook_deliveries` 表均不存在。
2. 文章主体仍保留。
3. 再次迁移到 v7，确认表和列恢复，文章 `version=1`。

迁移 006/007 的 Down 会分别删除投递表和版本列，是数据破坏性操作；本结果仅证明隔离演练路径可执行，不改变生产回滚前必须备份和停写的要求。

## 第一轮：发现恢复后搜索缓存缺陷

基线镜像创建备份 `db-20260730-035753.sql`：

| 项 | 值 |
|---|---|
| 大小 | 98,774 bytes |
| SHA-256 | `22229d42a355818a606c5179cf8a95a5d862e48034d81fce91b29178bbe3733f` |
| schema 版本 | v7 |

清空 public schema 后，CLI 成功恢复 30 张表和业务数据；管理员登录、文章列表、文章详情和媒体接口均正常。然而启动日志为 `search index warmed up indexed=0`，公开搜索和手动重建均返回 0。

根因是 `ArticleService.ReindexAll` 通过带缓存的文章列表服务取数，命中了恢复前写入 Redis 的空列表。数据库恢复正确，但旧缓存使搜索重建读到了过期结果。

## 修复内容

1. `ArticleService.ReindexAll` 分页直读 Repository，绕过列表缓存。
2. 缓存驱动新增逻辑前缀删除；数据库恢复只删除 `articles:` 与 `contenttype:`，不执行全前缀清空。
3. CLI 恢复成功后连接配置中的缓存后端并清理数据缓存；缓存不可用或清理失败时以非零状态退出，并明确提示数据库可能已经恢复。
4. HTTP 恢复同样执行定向缓存清理，并在失败时返回 `cache_warning`。
5. PostgreSQL 备份增加 `--no-owner --no-privileges`。
6. PostgreSQL 恢复增加 `ON_ERROR_STOP=1` 与 `--single-transaction`。
7. 目标 schema 为空时仍从当前模型注册表推导预期表集合，并要求备份包含可识别的 `schema_migrations` 证据。
